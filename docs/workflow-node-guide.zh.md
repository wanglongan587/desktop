## 1. 快速上手

五分钟跑通第一个工作流:

1. **打开编辑器。** 侧边栏点「工作流」(Alpha 标记)进入工作流库;主区域变为画布。
2. **新建工作流。** `Ctrl/Cmd+N` 或列表 `+` 菜单 → 新建工作流。新草稿自带一个「开始」节点。
3. **添加节点。** 画布底部的节点栏按执行顺序展示可用节点:开始 → Agent → 条件分支 → 变量聚合器 → 迭代 → 循环 → 输出。点击添加到画布中央,或按住拖到指定位置。
4. **连线。** 从节点右侧端口拖到下一节点的左侧端口。连线即执行顺序;画布是一个有向无环图,引擎按拓扑序调度。
5. **配置并发布。** 点选节点在右侧检查器配置参数(草稿自动保存);点「发布」把草稿固化为一个不可变版本并设为生效版本。
6. **运行。** 在项目或任务行的 `+` 菜单 → 「运行工作流」,选择已发布的工作流,填写启动输入后启动。运行冻结当时的生效快照,之后的草稿编辑不影响已启动的运行。

> **提示**:在实测的安装版 Ora 0.3.0 工作流库里,「迭代处理需求清单」和「循环检查代码片段」两个示例开箱即可运行,见[第 5 节](#5-示例实战)的逐步拆解。

## 2. 核心概念

### 2.1 画布、节点与连线

- **节点**是执行单元;**连线**定义先后依赖。引擎从「开始」节点沿连线做拓扑排序,前驱全部完成后节点才会就绪;同一层就绪的节点并行执行。
- **只有从开始节点可达的子图会执行。** 画布上可以保留未连线的备用节点和备用分支——它们不进入调度、不进变量池、不建会话;编辑器和运行全图会标注「未参与运行」。重新连线即可恢复执行。
- 连线不能成环(图必须无环);跨容器区域(迭代/循环)边界的连线会被拒绝。
- 画布支持指针/手型模式、框选、滚轮缩放、小地图、「整理节点」自动布局、注释便签,以及会话级撤销/重做(离开编辑器即清空,自动保存不受影响)。

### 2.2 草稿与版本

每个工作流恰有一个**草稿**(可编辑工作区,自动保存)和任意多个**已发布版本**(不可变快照):

| 操作         | 行为                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------- |
| 发布         | 复制当前草稿为新快照,立即设为**生效版本**;之后新建的运行都用它                                                  |
| 版本历史     | 预览任意历史版本(只读);「恢复到此版本」把该版本图复制回草稿,不改变生效版本                                      |
| 设为生效版本 | 把生效指针切到某个历史版本,并把它的图同步进草稿                                                                 |
| 删除版本     | 可删除单个已发布版本;草稿和当前生效版本不可删                                                                   |
| 导入 / 导出  | `.reactflow.json` 文件;导入前预览、解析失败精确定位、缺失插件只警告不阻塞;导出只记录插件 ID 与启用状态,不含密钥 |

正在运行中的运行会冻结其快照:被运行引用的版本不可删除,所属工作流在有活跃运行时不可删除。

### 2.3 变量系统

变量是节点之间传递数据的唯一通道。

**选择器与模板语法。** 每个变量由「节点 ID + 变量名(+ 可选嵌套路径)」定位。在提示词等文本里用 `{{#节点.变量#}}` 引用,例如:

```text
当前需求:{{#iteration-1.item#}}
上一轮报告:{{#loop-review.report#}}
代码:{{#start.source#}}
对象字段:{{#iter.item.note#}}        ← array[object] 的元素按路径取字段
结构化字段:{{#agent-1.structured_output.body#}}
```

**变量从哪来。** 节点检查器里的「插入变量」菜单按来源分组列出:

- **全局变量**(见下);
- **沿执行路径的上游节点**产生的变量——不只是直接前驱,也包括更早的祖先节点(条件分支是"透明"的:穿过条件节点后能看到条件节点前驱的变量,但条件节点本身不产出变量);
- **作用域隔离规则**(容器节点):
  - 迭代区域内的成员能看到 `item`/`index` 轮次绑定、迭代节点上游的变量、区域内上游产物;**看不到**迭代节点自己暴露的 `output`/`entries`/`failed_count`。
  - 迭代区域外的消费者能看到迭代节点暴露的三个变量;**看不到**区域成员的产物和 `item`/`index`。
  - 循环体内的成员能引用循环携带变量(`{{#循环ID.变量名#}}`)、循环边界外的可见变量、体内上游产物。

> **提示(编辑器菜单的已知限制)**:上述作用域是运行时的准确规则,但当前编辑器的「插入变量」菜单在循环体内只列出全局变量和体内上游产物——携带变量与外部变量需要手动输入(默认循环模板与两个示例正是这么写的);循环的命名导出同理,菜单里显示的是运行时不认可的通用 `{循环ID}.output` 条目,引用循环输出时请手动输入命名导出名(如 `{{#loop-review.final_report#}}`)。

**值类型。** 变量有静态类型,在图解析、编辑器录入、运行池写入三处统一校验。完整类型表见[附录 A](#附录-a值类型)。

**全局变量与系统变量。** 工具栏「全局变量」对话框管理系统变量与自定义全局变量:

- 系统变量 `sys.workflow_id`(当前工作流 ID,string)与 `sys.timestamp`(运行创建时的时间戳,number;应用重启后恢复执行时会刷新)由运行时提供,只读;
- 自定义全局变量要求**带点号的名称**(如 `cfg.threshold`)、明确的类型和类型正确的初始值,保存后全图可用,不依赖连线拓扑。

**文件类型。** `file` 是工作区相对路径的持久引用,结构为 `{"kind": "workspace_file", "path": "相对路径"}`;`array[file]` 是其数组。绝对路径、`..` 穿越、空路径、平台保留名都会被拒绝。

**运行时校验。** 模板渲染时引用的变量必须**已声明且已赋值**;否则该节点以 `prompt_template` 失败("提示词模板无法渲染"),绝不渲染成空串。并行分支中的节点引用尚未完成的兄弟分支变量因此是危险的——按拓扑序,兄弟分支可能还没赋值。

### 2.4 节点总览

| 节点                           | 执行形态   | 一句话用途                       | 可放置位置                            | 对外暴露的变量                                                                             |
| ------------------------------ | ---------- | -------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------ |
| 开始 Start                     | 即时       | 定义工作流输入与启动指令         | 顶层(每图恰一个)                      | `{id}.input` + 各输入变量                                                                  |
| Agent                          | 异步(会话) | 把一步工作交给模型自主完成       | 顶层 / 迭代区域 / 循环体              | `{id}.output`(最终回答文本);启用结构化输出时另有 `{id}.structured_output` 及字段路径       |
| 条件分支 Condition             | 即时       | 按规则选择后续路径(IF/ELIF/ELSE) | 顶层 / 迭代区域 / 循环体              | 无(透传前驱变量)                                                                           |
| 变量聚合器 Variable Aggregator | 即时       | 把互斥分支的输出合并为一个变量   | 顶层 / 迭代区域                       | `{id}.output`(候选共同类型)                                                                |
| 迭代 Iteration                 | 复合区域   | 对数组逐元素执行区域内节点       | 顶层                                  | 区域外:`{id}.output`、`{id}.entries`、`{id}.failed_count`;区域内:`{id}.item`、`{id}.index` |
| 循环 Loop                      | 复合区域   | 反复执行循环体直到满足结束条件   | 顶层                                  | `{id}.{携带变量名}`(体内)、`{id}.{输出名}`(输出绑定)                                       |
| 退出循环 Exit loop             | 即时       | 提前结束所在循环                 | 仅循环体(从成员输出端口 `+` 菜单添加) | 无                                                                                         |
| 输出 Output                    | 即时       | 汇总最终结果                     | 顶层 / 循环体                         | 无(消费变量)                                                                               |

「即时」节点在同一调度波内同步完成;「异步」节点驱动一个真实的 Agent 会话;「复合」节点拥有一个区域子图,自己管理轮次。工具类节点(工具、汇合、人工确认、子流程)在运行时支持接入前不出现在节点栏。

## 3. 节点详解

### 3.1 开始(Start)

工作流的唯一入口,不可删除;节点栏中「开始」在已存在时置灰。

**配置项:**

- **初始 Prompt**:工作流的默认启动指令。启动运行时若不另行填写「启动输入」,运行就继承这段文本,并写入 `{start}.input` 变量。
- **输入变量**:启动运行前需要收集的强类型输入。每个变量包含:

| 字段               | 说明                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------- |
| 变量名             | 不含句点、全图唯一;运行时以此名报错(而不是显示名)                                        |
| 显示名称           | 启动输入表单里展示的字段名(可选)                                                         |
| 值类型             | 见[附录 A](#附录-a值类型)                                                                |
| 字段类型(表单控件) | 文本 / 段落 / 下拉选项 / 数字 / 复选框 / 单文件 / 文件列表 / JSON,决定启动时渲染什么控件 |
| 初始值             | 可选;留空则部署后填写。下拉选项的初始值必须是已有选项                                    |
| 必填               | 勾选后启动时必须提供                                                                     |
| 最大长度           | 仅 string/secret,正整数;编辑器默认值与运行输入都受限                                     |

**控件与值类型的对应关系:**

| 控件        | 产生的值类型                                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文本 / 段落 | string                                                                                                                                                        |
| 下拉选项    | string(取值限于配置的选项)                                                                                                                                    |
| 数字        | number                                                                                                                                                        |
| 复选框      | boolean                                                                                                                                                       |
| 单文件      | file                                                                                                                                                          |
| 文件列表    | array[file]                                                                                                                                                   |
| JSON        | object / any / array / array[string] / array[number] / array[object] / array[boolean] / array[any](不能声明 array[file]);初始值与运行输入都必须匹配声明的类型 |

**典型用法。** 用「文本/段落」传自由文本,用「JSON + array[object]」传给迭代用的对象数组,用「下拉选项」把枚举值钉死(防止运行时拼错),用「单文件/文件列表」传工作区文件。

**边界校验(实测行为)。** 启动时的输入校验失败以 `workflow_run_input_invalid` 公开错误报出,携带**变量名与原因**;一次提交只报**字典序第一个**被拒值,且不落任何值——每次保存都精确指向一个要修的字段:

- 值与声明类型不符(如 number 收到字符串、object 收到数组);
- 未知的变量名;
- 下拉选项收到选项之外的值("value is not one of the configured options");
- 必填值缺失("required value is missing");
- 文件路径不安全(绝对路径、`..` 穿越)。

### 3.2 Agent

唯一"干活"的节点:为它创建一个真实的 Agent 会话(独立的 CLI Agent 进程),在运行选中的工作区里执行提示词描述的任务。

**配置项:**

- **Agent 模型**:选择执行器(Agent CLI)与模型。组合形式如 `OpenCode · Sonnet`。
- **角色**:可选。角色会作为行为约束注入会话;选「无角色」则不注入。
- **自定义 Prompt**:任务指令模板。支持「插入变量」;上游节点的输出**不会**隐式追加——只有你在模板里显式引用(如 `{{#agent-1.output#}}`)才会进入提示词。
- **必需 Skill**:声明的技能会安装到工作区,并在节点提示词开头以斜杠命令形式强制调用。它是"必须调用"的契约而非安全隔离——工作区里其他已物化技能对 Agent 依然可见。启用一个不存在的技能会在**创建运行时**被拒绝(`workflow_skill_not_found`)。
- **允许的 MCP**:从已安装的 MCP 插件中挑选并启用。**只有在此启用的 MCP 才会授权给该节点的会话**(严格允许列表);一个都不选 = 不使用任何 MCP 服务器;启用了但插件缺失/不可用 → 节点显式失败,绝不静默跳过。普通聊天不受影响。
- **交互模式**:开启后节点首轮结束停在「等待参与」,可以在节点会话里持续对话(人在环节)。迭代区域与循环体内的 Agent 不能开启交互模式(编辑器直接禁用开关)。
- **结构化输出**:配置一个以 object 为根的 JSON Schema(可视化字段编辑器或原生 Schema 编辑器,二者编辑同一份草稿,保存才落盘)。约束只作用于**最终回复**——Agent 仍可推理、调用工具、改文件,但最后一条助手消息必须是一个裸 JSON 对象。校验通过后写入 `{id}.structured_output`(字段路径在选择器中逐级展开);校验失败则节点以 `structured_output` 失败,但 `{id}.output` 仍保存原始回答文本供排查。
- **失败自动重试**(0.3.0 之后新增):开关 + 最多重试次数(0–5) + 首次等待秒数(0–300)。未配置时使用默认策略:启用、最多 2 次、首次等待 10 秒。等待按 2 倍指数退避,上限 600 秒。**只有这些失败会被重试**:智能体会话失败、会话异常结束、会话未能建立、结构化输出不合格、智能体拒绝请求、未知的停止原因。重试不会回滚文件改动;重试的新尝试会带上一次失败的原因(对回复类失败);交互模式节点永不重试;其他失败种类(如模型不可用、提示词模板错误)一次即失败,失败块会注明"此类失败不会自动重试"。

**暴露变量:** `{id}.output`(string,最终助手回复文本——不含注入的工作流上下文块)、`{id}.structured_output`(object,启用时)及字段路径。

**运行输出地位:** 若全程没有输出节点完成,已完成的 Agent 节点可兜底成为运行的最终输出。

### 3.3 条件分支(Condition)

按规则把执行路由到不同分支:IF(可多个 ELIF)+ 默认分支(ELSE)。

**配置项:** 每个分支(case)包含:

- **分支逻辑**:「满足以下所有条件」(AND)或「满足以下任一条件」(OR);
- **条件规则**列表:变量(从可见变量中选) × 运算符 × 值。取反语义通过选择互补运算符表达(如「不等于」「不包含」)。

**求值语义(实测行为):**

- 分支按声明顺序求值,**第一个命中的分支胜出**。两个分支条件重叠时,排在前面的赢——场景套件专门钉死了这一行为。
- 没有任何分支命中时走**默认分支**;若没有连接默认分支节点,则该条件节点之后没有节点执行。
- 每个分支至少一条规则才能参与匹配;空规则的分支(还没点「添加条件」)直接跳过,不会"空条件恒真"抢走 ELSE。
- **未赋值变量**:`为空`/`不为空` 容忍未赋值(未赋值视为空);其余运算符遇未赋值变量直接让节点以 `condition_evaluation` 失败("条件无法判断"),绝不猜测分支。
- **类型不匹配**同样是失败而非假值:比如对 string 用「大于」。

**运算符:** 界面提供 12 个(等于、不等于、包含、不包含、开头是、结尾是、大于、小于、大于等于、小于等于、为空、不为空),语义见[附录 B](#附录-b比较运算符)。引擎层另接受 `is`/`is_not`(布尔等值)与 `exists`/`not_exists`(变量是否已赋值),主要服务于导入图与循环节束条件。

**透明性:** 条件节点不产出任何变量;它的下游看到的是条件节点**前驱**的变量——穿过一串条件节点链同样成立。分支选择是调度器私有状态,不进变量池。

### 3.4 变量聚合器(Variable Aggregator)

把**互斥分支**各自的输出合并成一个变量,让汇合后的下游只引用一个名字。

**配置项:**

- **候选变量**:有序列表,每项是一个分支产出的变量(如 `branch-a.output`、`branch-b.output`)。**声明顺序即优先级**,可上移/下移调整。

**语义:**

- 运行时取**第一个已赋值**的候选,原值透传为 `{id}.output`。"已赋值"指变量池里存在这个键——**不是真值判断**,`false`、`0`、`""`、`[]`、`{}`、`null` 都算已赋值并会命中。
- 所有候选类型必须一致(解析期校验),`{id}.output` 以该共同类型声明。
- 候选必须是其静态传递前驱(互斥的兄弟分支符合条件)或全局变量产出的。
- **全部候选都未赋值 → 节点失败**(稳定的 `aggregator_no_match`)。换句话说聚合器只做"多选一透传",不做默认值兜底——需要兜底就在每个分支都保证赋值。

**何时不用它:** 如果分支不是互斥的(可能同时执行),聚合器会拿到"先完成者"而非"计划者";并行汇合场景请改用两个分支各自连到不同下游,或用输出节点分别汇总。

### 3.5 迭代(Iteration)

对数组源**逐元素**执行区域内子图——foreach 语义。它是画布上的嵌入式复合区域:成员通过区域左端的固定「内部起点」、内部连线插入、未连接输出端口的追加菜单添加;外部节点不能拖入区域,成员也不能拖出。

**配置项:**

| 字段     | 说明                                                                    |
| -------- | ----------------------------------------------------------------------- |
| 迭代源   | 一个数组类型的变量(如 `start.requirements`、某 Agent 的结构化数组字段)  |
| 收集目标 | 区域内声明的根变量(通常是区域末端的 `{成员}.output`),每轮取它的值       |
| 错误策略 | `fail`(默认):任一轮失败即失败整个运行;`continue`:失败轮记入账本并继续   |
| 最大轮次 | 默认 50,最小 1;**源长度超过它 → 迭代节点在启动边界即失败**,绝不静默截断 |

**轮次绑定与产物:**

- 每轮为区域注入 `{迭代ID}.item`(当前元素,类型跟随数组元素类型)与 `{迭代ID}.index`(从 0 开始的序号)。区域内提示词直接引用,如 `{{#iteration-1.item#}}`;`array[object]` 的元素还能按路径取字段(`{{#iter.item.note#}}`)。
- 完成后对外暴露三个变量(错误策略不影响类型):

| 变量                    | 类型          | 含义                                                   |
| ----------------------- | ------------- | ------------------------------------------------------ |
| `{迭代ID}.output`       | array[T]      | 收集目标逐轮收集的值数组,T 为收集目标声明类型          |
| `{迭代ID}.entries`      | array[object] | 与源数组对齐的逐轮台账 `{item, status, output, error}` |
| `{迭代ID}.failed_count` | number        | 失败轮数                                               |

**边界行为(实测行为):**

- **空数组**:合法。零轮次、零会话,立即以空输出完成。
- **超上限**:启动即失败,错误含元素个数与上限以及调整指引。
- **收集目标被绕过**:`continue` 策略下某轮的条件分支绕开了收集目标,该轮按**失败轮**结算("collect target did not run this round"),不会读上一轮的陈旧值;`{id}.output` 只含真正执行过的轮次。
- 区域内不能再放输出节点、迭代或循环节点(不能嵌套复合);成员的出边必须留在区域内;外部节点不能连向成员。
- 区域内 Agent 不能开交互模式(新成员默认关闭;旧图的交互成员会有"关闭交互模式"修复按钮,不修则发布被拒)。
- 每轮是独立的执行作用域:同一定义节点在每轮有独立的节点运行记录与会话,互不覆盖;区域内的条件决策按轮记录。

**编辑体验:** 区域可折叠/展开(折叠只影响显示)、手动拖角调整大小(20 像素网格,最小 560×340)、「整理节点」时区域内外分别布局。删除非空区域会确认成员数量并级联删除成员与相关连线(可撤销);删除收集目标节点会清空该选择器并提示重新配置。运行视图中,区域成员按 `(节点, 轮次)` 分组,提供轮次选择器查看任意一轮的会话与状态。

**恢复语义:** 迭代节点是恢复单元——区域内任何失败,从失败处继续都会清掉整个迭代的轮次记录与产物并**从第 1 轮重跑**;不支持轮内续跑。

### 3.6 循环(Loop)与退出循环(Exit loop)

**重复执行直到满足条件**的反馈容器。与迭代的区别:迭代是"对每个元素做一遍"(轮次数由数组决定),循环是"把上轮结果带回下轮反复做"(轮次数由结束条件决定)。

添加循环节点时,编辑器自动生成一个合法容器组:**循环节点 + 子开始(「轮次开始」)+ 子 Agent(「循环 Agent」)**,并预置一套默认配置——携带变量 `value` 初始为空串、每轮把子 Agent 输出回写进 `value`、子 Agent 输出不为空即停、并把子 Agent 输出导出为 `result`。

**循环配置(loopConfig):**

| 字段           | 说明                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最大轮次       | 1–100。达到上限仍未满足结束条件 → **循环失败**                                                                                                    |
| 携带变量       | 有类型的跨轮变量:名称 + 类型 + 初始值(常量或入口处求值的选择器) + 反馈选择器(每轮结束后把该选择器的值写回变量)。体内用 `{{#循环ID.变量名#}}` 引用 |
| 结束条件 until | AND/OR 组合的规则,可用变量:子节点输出(含结构化字段)、携带变量、循环边界外可见变量。**每轮结束后求值**:命中 → 循环成功;未命中 → 下一轮             |
| 输出           | 循环成功时导出的变量绑定(名字 + 选择器),导出为 `{循环ID}.{输出名}`                                                                                |

> **注意**:循环对外只暴露「输出」列表里命名的导出(`{循环ID}.{输出名}`,如 `loop-review.final_report`)。当前编辑器的变量菜单对循环节点只显示一个通用的 `{循环ID}.output` 条目——运行时并不认可它(引擎只为命名导出赋值),请手动输入导出名;示例工作流的输出节点就是这么写的。

**轮次语义(实测行为):**

- 每轮一个持久作用域,子节点运行记录按轮隔离;舞台的循环检查器可切换轮次查看每轮子节点状态与会话。
- 结束条件在**每轮完成后**求值,不是轮中;首轮就可能满足并立即成功。
- **触顶失败**:达到最大轮次仍未满足,循环以 "Loop did not terminate within N rounds" 失败(见[第 5.2 节](#52-循环检查代码片段循环节点的真实触顶案例)的真实案例)。这是刻意设计——它防止"永远差一点"的循环静默吞掉轮次预算。
- 空值/存在性检查(`为空`/`不为空`)容忍未赋值变量;其余比较遇未赋值直接失败,**绝不复用上一轮的旧值**——反馈链断了会响亮地失败。
- 输出绑定的选择器在结算时必须已赋值,否则循环失败。

**循环体的规则:** 体内是独立 DAG,恰有一个可达的子开始节点;可放 Agent、条件分支、输出、退出循环;**不能嵌套**循环或迭代;边不能跨循环边界;携带变量和边界外可见变量在体内可用。

**退出循环(Exit loop)。** 从循环成员输出端口的 `+` 菜单添加,归属该循环,只进不出(无输出端口)。到达退出节点会**提前结束所在循环**(不是整个工作流):调度器优先派发就绪的退出节点,取消同轮仍在跑的兄弟节点,按当前已提交轮次冻结输出并发布。典型用法是「条件分支 → 满足时连退出循环」实现"达到某个业务状态就提前收手"。可以完全删掉结束条件、只靠退出节点控制循环;但两者都没有时,上限仍会兜底失败。

**恢复语义:** 循环节点是恢复单元——体内任何失败(含被放弃的重试等待)都会清掉全部轮次记录与产物,**从第 1 轮重跑**;「只回滚失败节点文件」对该单元不可用(`composite_region`),「整体回滚到检查点」恢复到进循环前的工作树。

### 3.7 输出(Output)

终端节点:把若干变量组装成运行的最终结果对象。必须终端放置(不能有出边)。

**配置项:输出结果**绑定列表——每项是「结果名 + 结果变量」(如 `review_report` ← `loop-review.final_report`)。结果名的作用域是本节点;不同分支上的多个输出节点可以复用同名结果,各算各的。

**运行最终输出的裁决顺序:**

1. 有已完成的输出节点 → 其结果对象是运行的最终输出;若多个输出节点都完成(不同分支各自到达终点),取最近完成的那个;
2. 否则已完成的 Agent / 迭代节点兜底(并列时同样取最近完成的);
3. 条件分支、聚合器、退出循环、子开始等控制节点永不贡献运行输出。

输出节点放在循环体内时,导出的是该轮视角的绑定值;更常见的做法是在循环外放一个输出节点引用循环的导出变量(5.2 的示例即如此)。

## 4. 运行与观测

### 4.1 启动一次运行

从**项目行**或**任务行**的 `+` 菜单 → 「运行工作流」(只列出已发布的工作流)。运行在该行对应的工作区执行:项目行 → 主工作区;任务行 → 该任务的隔离工作区。后端不推断分支、不另建工作树。

启动对话框收集:

- **运行名称**(默认工作流名);
- **启动输入(可选)**:覆盖开始节点初始 Prompt 的本次指令,写入 `{start}.input`;
- **启动变量表单**:开始节点声明的每个输入变量按其控件渲染,必填校验与类型校验见 [3.1](#31-开始start)。

点「启动」后:运行冻结当前生效快照、初始化变量池、按图开始调度。开始节点声明的变量若未填初始值,这里是唯一填写时机。绑定到节点运行的会话不出现在普通聊天列表;终态节点的会话只读。

### 4.2 运行视图:舞台与全图

- **舞台(Theater)**:聚焦当前节点的话剧舞台 + 左侧执行路径轨道 + 右侧节点检查器(只读展示配置、错误、产物)。并行节点可用芯片/方向键切换;舞台卡片内嵌**会话坞**——展开即在卡片内看到完整对话气泡与 Markdown 渲染,思考与工具调用折叠在活动披露里。循环运行提供轮次切换与轮次历史;迭代提供区域轮次选择器。
- **全图(Overview)**:按发布快照渲染整图,节点着色显示状态,支持缩放与拖拽;迭代区域按 `(节点, 轮次)` 分组展示,点击任意节点查看该轮明细。

### 4.3 节点与运行状态

| 状态                       | 含义                                                                      |
| -------------------------- | ------------------------------------------------------------------------- |
| 未运行 Pending             | 尚未开始(没有节点运行记录)                                                |
| 运行中 Running             | 正在执行                                                                  |
| 等待参与 AwaitingInput     | 交互模式 Agent 停在等待人工输入;侧边栏会提示需要人参与                    |
| 等待重试 Waiting to retry  | 失败自动重试的等待窗口(橙色、显示倒计时与尝试序号),期间没有任何东西在执行 |
| 未激活分支 Inactive branch | 条件分支未选中一侧的下游节点,本次运行不会执行                             |
| 成功 Succeeded             | 完成                                                                      |
| 失败 Failed                | 失败(运行随之失败,但在途兄弟节点会跑完且保持可绑定)                       |
| 已取消 Cancelled           | 被取消                                                                    |

失败即停(D2 语义):任一根层节点失败,运行立刻失败,调度器不再派发新节点;已派发的在途节点跑到终态。运行内任何已提交的节点/节点运行状态变化都会发布失效事件,前端轮询兜底刷新(约 1.5 秒)。

### 4.4 失败、重试与恢复

**失败详情。** 失败节点的检查器展示:失败种类(18 类,见[附录 C](#附录-c失败种类))、消息、底层错误链、尝试序号;其下按时间列出**更早的失败尝试**,并标注每个尝试最终被什么替代:自动重试、手动恢复,还是从头重跑。每个节点运行前都会在工作树打一个 git 检查点(`refs/ora/checkpoints/<node_run_id>`),并记录文件改动清单。

**三个恢复入口:**

1. **从失败处继续(Resume)**:软删失败的节点运行及其后代,从幸存状态重排。对话框可选回滚模式:
   - 保留现状(默认):不动工作树;
   - 只回滚失败节点改过的文件:按失败节点记录的文件改动恢复;
   - 整体回滚到检查点:恢复整个工作树到恢复单元执行前(回滚前会自动再存一个 `pre-rollback-*` 快照,可反悔)。
   - 失败在迭代/循环区域内时,恢复单元是整个容器节点,轮次从 1 重来;`只回滚文件` 对容器不可用。
2. **从头重新运行(Restart)**:轮换执行身份重跑整个运行,旧历史保留但不再影响调度。
3. **换新版本继续**:失败的运行可以切到更新的已发布版本继续,引擎会做图兼容性检查(删节点、改节点类型、改开始节点契约、改变量类型等不兼容,并给出具体原因)。

**前次失败注入。** 默认开启:同一节点同一次执行的前次失败(若属于回复类失败)会被注入新尝试的提示词,告诉 Agent 上一次为什么失败;结构化输出不合格、拒绝执行就是典型受益者。运行级开关可关闭。

## 5. 示例实战

以下两个示例来自实测的安装版 Ora 0.3.0 工作流库,开箱即可运行。我们对两者都做了真实运行验证:一个完整成功,一个真实触发循环触顶失败——两个结果都拆给你看。

### 5.1 迭代处理需求清单(迭代节点,成功案例)

**目标**:把 3 条需求逐条交给 Agent 落实,并汇总每条的处理结果。

**图结构:**

```text
┌────────┐   ┌──────────────────────────────┐   ┌────────┐
│  开始  │──▶│ 迭代:逐条处理需求            │──▶│ 输出   │
│        │   │  ┌────────────────────────┐  │   │        │
│ source │   │  │ (内部起点) ─▶ 需求实现 │  │   │results │
│ array  │   │  └────────────────────────┘  │   │        │
└────────┘   └──────────────────────────────┘   └────────┘
```

**关键配置:**

- 开始节点:输入变量 `requirements`,类型 `array[string]`,默认值是 3 条中文需求;
- 迭代节点:迭代源 `start.requirements`;收集目标 `process-1.output`;错误策略 `fail`;最大轮次 3;
- 区域内 Agent 提示词(节选):

  ```text
  你要逐条落实需求清单中的一条需求。

  当前轮次序号(从 0 开始):{{#iteration-1.index#}}
  当前需求:{{#iteration-1.item#}}

  请完成这条需求,并用一句话输出:改动内容 + 验证方式。
  ```

- 输出节点:`results` ← `iteration-1.output`。

**真实运行结果**(安装版实测):3 轮全部成功,每轮各建一个独立 Agent 会话,Agent 在运行工作区留下了真实的文件改动(每轮都有 git 检查点与改动记录):第 1 轮新建 `server.py`(+113 行)与 `tests/test_health.py`(+125 行),第 2 轮扩展 `server.py` 并新增 `tests/test_upload.py`(+150 行),第 3 轮补充 `README.md`(+33 行)。最终输出为 3 个元素的结果数组:

```json
{
  "results": [
    "改动内容:因仓库原本不存在 /health 接口,新建了纯标准库实现 server.py …",
    "改动内容:在 server.py 新增 POST /upload 文件上传接口 …",
    "改动内容:在 README.md 补充了「本地启动步骤」章节 …"
  ]
}
```

要点:轮次绑定在**每轮的提示词里**渲染,`index` 从 0 计;收集目标逐轮聚合;输出节点一步引用聚合数组。

### 5.2 循环检查代码片段(循环节点的真实触顶案例)

**目标**:反复审查同一段代码,每轮把上轮报告带入下一轮,直到报告确认没有遗留问题(输出 PASS),最多 3 轮。

**图结构:**

```text
┌────────┐   ┌────────────────────────────────────┐   ┌──────────┐
│  开始  │──▶│ 循环:循环审查与修复                │──▶│ 输出     │
│        │   │  ┌────────────┐   ┌────────────┐   │   │          │
│ source │   │  │ 轮次开始   │──▶│ 代码审查员 │   │   │review_   │
│ string │   │  └────────────┘   └────────────┘   │   │report    │
└────────┘   └────────────────────────────────────┘   └──────────┘
```

**关键配置(loopConfig):**

- 携带变量 `report`(string,初始空串),反馈选择器 = 审查员 Agent 的 `output`——每轮结束把本轮报告写回 `report`;
- 结束条件:审查员输出 **contains** `"PASS"`;
- 最大轮次 3;
- 输出:`final_report` ← 审查员 `output`;
- 审查员提示词(节选)引用了**跨边界变量** `{{#start.source#}}`(待查代码)与**携带变量** `{{#loop-review.report#}}`(上轮报告),并要求"没有遗留缺陷时在报告最后单独一行输出 PASS"。

**真实运行结果**(安装版实测):3 轮审查全部执行、Agent 每轮都成功产出了报告,但三轮报告都没有出现 PASS——循环在 3 轮上限处失败:

```text
Loop did not terminate within 3 rounds
```

这正是文档 [3.6](#36-循环loop与退出循环exit-loop) 描述的触顶语义:结束条件在每轮后求值,不满足就烧一轮,上限耗尽即失败。三个处置选项:

1. **提高上限**:最大轮次最高 100,给收敛留余地;
2. **让收敛信号更确定**:在提示词里钉死报告格式(比如"报告必须以 DONE 开头"),结束条件改用「开头是」代替「包含」,减少误判;
3. **改用退出循环节点**:在循环体内放条件分支,判定"遗留缺陷数为 0"时连「退出循环」提前收手。

反过来说,这个失败设计是**保护性的**:如果上限耗尽被静默当作成功,你会拿到一份带着未收敛报告的结果而毫无察觉。

### 5.3 模板改造建议

- **把迭代示例升级为对象数组**:开始变量改成 `array[object]`(JSON 控件),提示词里用 `{{#iteration-1.item.title#}}` 取字段;收集目标不变。
- **给两个示例加条件过滤**:在迭代区域内 Agent 后放条件分支,不满足的轮次绕过收集目标(记得把错误策略切到 `continue`,并理解被绕过的轮按失败轮记账,见 [3.5](#35-迭代iteration))。
- **给循环加自动重试**:审查员是普通 Agent 节点,打开「失败自动重试」,会话类失败会自动重跑而不用人工恢复。
- **复制而非破坏**:列表行的「···」操作菜单里点「复制」,得到一个可编辑、未发布的副本,原模板保持可用。

## 6. 组合场景配方

以下配方全部来自 22 个生产级场景测试(在最新 main 上全量通过),每个都给出结构骨架与关键配置。测试通过真实后端接口驱动:创建 → 发布 → 运行 → 填启动输入 → 轮询终态,Agent 由 fake 插件执行但回答语义与真实 Agent 对齐。

### 6.1 条件路由 + ELSE 兜底

```text
开始 ─▶ Agent(生成报告) ─▶ 条件分支 ─┬─ equals "critical" ─▶ 输出A(告警)
                                    └─ 其他情况(ELSE) ────▶ 输出B(普通记录)
```

要点:字符串相等用「等于」;未命中走默认分支;未激活分支零会话、输出节点各自绑定自己分支的变量。若分支条件故意重叠(如 `count > 3` 的两个分支),**首个分支胜出**——要么让条件互斥,要么有意利用首命中优先。

### 6.2 互斥分支聚合

```text
      ┌─ 条件分支 ─┬─ 分支1 ─ Agent-a ─┐
开始 ─┤            └─ 分支2 ─ Agent-b ─┴─▶ 变量聚合器 ─▶ 输出
```

聚合器候选 `[agent-a.output, agent-b.output]`,实际只有被执行的一侧赋值,聚合器取第一个已赋值者透传。注意 `false`/空串也算"已赋值";两侧都没跑会以 `aggregator_no_match` 失败。

### 6.3 迭代 + 区域内条件过滤

```text
开始(array[object] 的 PR 列表) ─▶ 迭代 ─ [内部起点 ─▶ Agent ─▶ 条件分支 ─┬─ needs_fix ─▶ Agent(修复, 收集目标)
                                                                      └─ 其他 ────────(绕过收集目标)
```

迭代源 `start.prs`(array[object]);区域内条件比较 `{{#iter.item.risk#}}`;错误策略 `continue`。被绕过收集目标的轮次按失败轮记入 `entries`,`failed_count` 可在输出节点引用。若不想让绕过算失败,就保证每轮都经过收集目标(比如在绕过分支上也放一个轻量 Agent)。

### 6.4 循环反馈收敛

```text
开始(draft) ─▶ 循环 [轮次开始 ─▶ 写作 Agent ─▶ 审校 Agent] ─▶ 输出
```

携带变量 `draft`(string),反馈选择器 = 审校 Agent 输出;写作提示词引用 `{{#loop.draft#}}` 实现草稿迭代;结束条件用审校输出 `contains "LGTM"`;输出导出终稿。类型化反馈同样支持 object/number——携带变量类型决定体内引用的渲染。

### 6.5 门控流水线(条件 → 迭代 → 循环 → 输出)

```text
开始 ─▶ 条件(门禁: mode equals "batch" AND threshold ≥ 1)
        ├─ 命中 ─▶ 迭代(过滤 + 收集) ─▶ 循环(反馈收敛) ─▶ 输出
        └─ 未命中(ELSE) ─▶ 输出(零会话直通)
```

三层容器按顺序串联(条件门 → 迭代 → 循环,均在顶层;循环不能嵌套进迭代区域)。作用域实测结论:循环体可以直接引用迭代暴露的 `output`(它是循环边界外的祖先变量,场景套件断言了这一点),开始节点的 object/array 值同样跨容器流入循环体;迭代区域内则用条件比较 `{{#iter.item#}}` 过滤元素,被过滤的轮次绕过收集目标。门未命中时走 ELSE 分支的输出节点,零会话直通完成。

### 6.6 结构化输出 × 迭代收集

迭代区域内的 Agent 开启结构化输出(JSON Schema 如 `{type:"object", properties:{fixed:{type:"boolean"}, note:{type:"string"}}}`),收集目标选 `{成员}.structured_output`,得到 `array[object]` 的类型化收集结果,输出节点直接绑定整个数组即可拿到全部结果。结构化不合格的轮次会以 `structured_output` 失败并触发自动重试,重试提示词会带上失败原因。

## 7. 最佳实践与常见陷阱

**变量与提示词**

- 只有**显式引用**的上游输出才会进入提示词;想串联步骤就写 `{{#agent-1.output#}}`,不要指望隐式注入。
- 引用未赋值变量 = 节点失败(`prompt_template`)。并行分支互引是雷区:拓扑序不保证兄弟先完成。
- 循环体内的提示词与循环输出的引用常常要手动输入:菜单当前只列出体内产物与全局变量,携带变量、外部变量、命名导出都要手写选择器(语法见 2.3)。
- 想跨拓扑共享配置,用带点号命名的自定义全局变量(如 `cfg.threshold`),别靠连线绕路。
- 条件分支链是透明的:穿过条件不影响可见变量;但条件节点自己的"走了哪条分支"拿不到——需要分支信息就让分支内的节点把标记写进自己的输出。

**开始节点**

- 枚举值一律用下拉选项:选项外的值在启动时被拒并点名变量,比自由文本 + 条件判断稳得多。
- JSON 控件的初始值必须匹配声明的值类型;声明 `array[object]` 就别放对象。
- string/secret 的最大长度约束同时管住编辑器默认值和运行输入。

**条件与聚合**

- 条件重叠时首命中优先——要么互斥,要么排序表达优先级。
- 未赋值变量只配 `为空/不为空`(或引擎级 `exists/not_exists`);其他运算符会直接失败,这是防止陈旧值误路由的保护。
- 聚合器不做默认值;需要兜底就给每个分支都赋值,或者干脆用 ELSE 分支保证必有一条路赋值。

**迭代**

- 源长度 > 最大轮次 = 启动即失败。源长度不定时把最大轮次设到安全上界(它只是保险丝,不是配额)。
- `continue` 策略下,绕过收集目标的轮按失败轮记账——`failed_count` 是判断"过滤了多少"的正确信号。
- 空数组是合法输入:零轮次直接完成,适合"可选批处理"场景。
- 迭代恢复必然从第 1 轮重来,别指望续跑某一轮;昂贵的轮内工作考虑拆成两次运行。

**循环**

- 先想清楚收敛信号再写循环:结束条件里的标记必须由循环体内的节点**确定性地**产出(提示词里钉死"单独一行输出 PASS"),否则就是 5.2 示例的触顶结局。
- 触顶失败是保险丝不是 bug:3 轮不收敛说明要么任务不收敛、要么信号写错了。
- 携带变量的反馈选择器指向"每轮结束时取谁的新值",链断了(未赋值)会响亮失败,不会拿旧值凑合。
- 循环体内可以放输出节点和退出循环;不能嵌套循环/迭代。
- 完全没有结束条件、只靠退出循环节点控制是合法的,但上限兜底仍然生效。

**Agent 与恢复**

- 交互模式节点是人在环节:适合审批、澄清;不适合无人值守流水线,且区域内不可用。
- 自动重试只覆盖会话类与回复类失败(共 6 类,见附录 C);模型不可用、提示词模板错误一次即败,需要人工介入。
- 重试不回滚文件——Agent 可能已经改了半截文件;对文件敏感的场景配合「从失败处继续 + 整体回滚到检查点」。
- 迭代/循环内的失败以容器为恢复单元,轮次从头来;`只回滚文件` 对容器不可用。

**版本与运行**

- 运行冻结快照:改草稿不影响在途运行;要应用新逻辑就发布新版本再开新运行,或对失败运行做版本切换恢复(有兼容性检查)。
- 删除工作流前先确认没有活跃运行(会被拒绝);被运行冻结的版本也删不掉。
