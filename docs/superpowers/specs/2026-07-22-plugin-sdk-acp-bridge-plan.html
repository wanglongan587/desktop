第 0 章这个方案是做什么的

Ora 是一个 AI 编程 IDE(像 VS Code 那样的桌面/网页工具,但内带 AI)。它支持装"插件",其中有一种插件叫 agent 插件——专门给你提供"能聊天的 AI 助手"。但 Ora 自己并不自带 Claude Code 这种 agent;本方案就是写一段"桥"代码,把你电脑上已经装好的 Claude Code(或 codex)接成 Ora 的 agent 插件,让你在 Ora 的聊天框里直接用上 Claude Code。一句话:让你不用离开 Ora,就能用它干活。

打个比方Ora 像一家餐厅,agent 插件像"会做菜的厨师"。但 Ora 自己没雇 Claude Code 这位厨师,只留了个"厨师工位"。本方案就是给这个工位配一个"翻译服务员"(桥):Ora 前台听不懂 Claude Code 说的方言(ACP),Claude Code 也听不懂 Ora 内部的话;翻译服务员站在中间,两边话互译,菜(对话)就流转起来了。

1.2 两种插件,本方案只做一种

Ora 的插件按"种类"分,清单里写死是哪种:

agent 插件(本方案做这个)workbench 插件(不做)
能干啥给你提供能聊天的 AI别的东西(面板/工具等)
v1 能跑代码吗能,开进程不能,只是目录里一条记录
有"开始对话"这个动作吗有没有(连进程都没)
回应一个常见误解有人问"workbench 插件是不是也要开始对话?"——不会。不同种类的插件用不同的一套方法,workbench 这套根本没"开始对话"这个方法。本方案只管 agent 这一种。

1.3 "启动插件"和"开始聊天"是两回事(重要,之前踩过坑)

这是最容易混的一点,必须先讲清。一个 agent 插件从装上到你和它聊上天,分三步,中间隔着你的一次回车:

  1. 第一步 · 登记(进程还没拉起来)
  2. ②
    装上插件,记进目录② 读插件清单,知道"有这么个 agent 插件、它声明了一个 provider"。此刻进程没开、还不能聊。
  3. ↓
  4. 第二步 · 启动插件(拉进程 + 激活)
  5. ②
    拉起 ③ 进程 + 握手 + 激活② 开一个 Bun 进程,握手(确认身份/版本),再调它的"激活"方法,让它把自己的能力(provider)报上来。到这步"插件启动完"——但还没聊任何天。
  6. ↓ ……你某天在聊天框打字、按回车 …… ↓
  7. 第三步 · 开始聊天(这才轮到"开始对话")
  8. ②
    ② 发"开始对话"请求你按回车,② 才把你的消息当成一次"开始对话"请求,经 Ora 协议送到 ③,③ 再交给桥去驱动 ④。这是"开始对话",不是"启动插件"。
为什么之前会看混因为"激活"有个"懒启动"模式:第一次你发消息时,② 会顺手把第二步(激活)和第三步(开始对话)连着做。两步挨在一起,看着像一步。但它们是两条独立的协议消息,各有各的超时(激活 15 秒、对话调用 60 秒)。"启动插件" ≠ "开始聊天"。

1.4 这个"桥"是什么

桥是一段住在 ③ 插件进程里的代码,干两件翻译活:

  • 把 Ora 的请求翻给 Claude Code:Ora 说"开始一轮对话(带这句 prompt)",桥翻成 ACP 的"开个会话 + 跑这一句"。
  • 把 Claude Code 的回吐翻给 Ora:Claude Code 边想边往外吐字、调工具、报用量;桥把这些翻成 Ora 认识的事件流,经 ② 流回你屏幕。

桥是可选脚手架——只在你"想包一个本地 ACP 说的 agent"时用。如果你接的是别的后端,可以手写 provider,不用这桥。

1.5 一轮聊天怎么走(人话版)

  1. ①
    你打字、按回车"帮我把这个函数重构一下" → 经 HTTP 送到 ②。
  2. ↓
  3. ②
    ② 经 Ora 协议把请求送 ③② 不管 ACP,只用 Ora 自己的话说"开始对话{这句话}"。
  4. ↓
  5. ③
    桥拉起 ④、开 ACP 会话、把 prompt 送给 ④桥用 ACP 话对 Claude Code 说"开个会话、跑这句"。
  6. ↓
  7. ④
    Claude Code 边想边吐一个字一个字往外吐、调工具(读文件/改代码)、报 token 用量……
  8. ↓
  9. ③
    桥翻译成 Ora 事件,流回 ② → ①吐的字 → "文本增量"事件;调工具 → "工具调用"事件;用量 → "用量"事件。你屏幕上字一个个冒出来、出工具卡片。
  10. ↓
  11. ④
    Claude Code 说"这轮说完了"给个收尾原因(正常结束/被取消/到上限)。
  12. ↓
  13. ③
    桥把这轮结果报给 ②,一轮结束续聊再发一句就走"发消息"(复用同一个 ④、同一个会话)。
第 2 章深入:技术细节(每段代码都讲为什么、什么意思)

下面进入代码。规矩:每段代码前有"为什么需要它",代码后有"什么意思"逐条解释。代码都在独立框里,不与正文混杂。

2.1 粘包/分包:两条"语言"怎么不串味

这是上一轮你问的问题,正式写进方案。为什么会串味:不管管道还是 TCP,操作系统只管"传字节",不管"哪几个字节属于一条消息"。所以可能发生两种情况——

  • 粘包:一次读出来的字节里,塞了好几条消息粘在一起。
  • 分包:一条消息被拆成好几段,分好几次读出来。

两条线用两种不同的"切消息"办法,各自处理这两种情况。

2.1.1 Ora 协议(②↔③):用"长度前缀"切

Ora 协议每条消息前面加 5 个字节的"长度头"(1 字节类型 + 4 字节大端长度),后面跟那么长的内容。读的时候:先读够 5 字节拿到长度,再读够那么长的内容。长度头就是"消息边界"。

为什么这么设计长度前缀法是抗粘包/分包的标准做法:读到长度就知道要凑多少字节,凑齐就是一整条;一次读出来多条,就一条条消费完。还能在读之前先校验长度合不合法,防止对端发个"假长度"骗我们分配巨大内存。
packages/plugin-runtime/src/transport/frame.ts · 逐块解码器(简化)
// 常量:5字节头,单帧上限8MB
export const FRAME_HEADER_BYTES = 5;
export const MAX_FRAME_BYTES = 8 * 1024 * 1024;

export class FrameDecoder {
  #header = new Uint8Array(FRAME_HEADER_BYTES);
  #headerFilled = 0;          // 头已凑齐几个字节
  #payload;                    // 凑齐头后,按长度申请的体缓冲
  #payloadFilled = 0;

  decodeChunk(chunk) {         // 每次管道吐一块就调一次
    const frames = []; let offset = 0;
    while (offset < chunk.length) {
      if (this.#payload === undefined) {                // 还在凑头
        const c = Math.min(5 - this.#headerFilled, chunk.length - offset);
        this.#header.set(chunk.subarray(offset, offset+c), this.#headerFilled);
        this.#headerFilled += c; offset += c;
        if (this.#headerFilled === 5) {                 // 头齐了
          const len = new DataView(this.#header.buffer).getInt32(1, false);
          if (len <= 0 || len > MAX_FRAME_BYTES) throw new RangeError("bad len");
          this.#payload = new Uint8Array(len);          // 校验过才分配
        }
      } else {                                          // 在凑体
        const c = Math.min(this.#payload.length - this.#payloadFilled, chunk.length-offset);
        this.#payload.set(chunk.subarray(offset, offset+c), this.#payloadFilled);
        this.#payloadFilled += c; offset += c;
        if (this.#payloadFilled === this.#payload.length) {  // 体齐了=一帧
          frames.push({ payload: this.#payload });
          this.#header = new Uint8Array(5); this.#headerFilled = 0;
          this.#payload = undefined; this.#payloadFilled = 0;
        }
      }
    }
    return frames;
  }
}
  • 代码什么意思
  • 分包(半头/半体):#headerFilled / #payloadFilled 跨多次 decodeChunk 累加——头被拆到好几次读也能凑齐;体同理。
  • 粘包(一读多帧):while (offset < chunk.length) 循环,一块里塞几帧就消费几帧。
  • 头没齐不解长度:只有 #headerFilled===5 才取长度,不会拿半个头当长度。
  • 抗巨型帧 DoS:先 throw 再 new Uint8Array(len) 之前校验 len ≤ 8MB,对端谎报 2GB 也不分配。
  • 留剩字节:状态都在实例字段里,一次没消费完的字节自动留到下次。
  • 半帧收尾:真实代码的 finish() 在 EOF 时若还有半帧,直接报错,不静默误解析。

2.1.2 ACP(③↔④):用"换行"切

ACP 每条消息是一行 JSON,行尾加 \n。读的时候:把字节攒进缓冲,看到 \n 就切出一条。换行就是"消息边界"。

为什么这么设计换行分隔简单、人类可读。前提是 JSON 里不能内嵌裸换行(compact JSON 用 JSON.stringify 生成,本就没有内嵌换行),所以 \n 是安全的边界。它同样能扛粘包(一行行切)和分包(没 \n 就继续攒)。
packages/plugin-sdk/src/acp/wire.ts · #pipeLoop 读端(含三处加固)
const MAX_LINE_BYTES = 8 * 1024 * 1024; // 单行安全上限,镜像 Ora 侧 8MB

async #pipeLoop(stream, onLine) {
  const reader = stream.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    if (value === undefined) continue;
    buffer += decoder.decode(value, { stream: true });   // 多字节字符跨块用 stream:true
    if (buffer.length > MAX_LINE_BYTES) {               // 本轮补:超长无换行=失控
      this.#handleExit(null, null);                        // 当作 ④ 出错,拒掉在飞请求
            try { this.#proc?.kill(); } catch {}      // 尽力杀 ④
      return;
    }
    let nl;
    while ((nl = buffer.indexOf("\n")) !== -1) {           // 粘包:一读多行逐行吐
      const line = buffer.slice(0, nl).replace(/\r$/, ""); // 去 CR(CRLF 兼容)
      buffer = buffer.slice(nl + 1);                        // 剩余留下次(分包)
      try { onLine(line); }
      catch (e) { this.#handlers.onStderr(`[acp:handler-error] ${e}`); }
    }
  }
  buffer += decoder.decode();                              // flush 多字节尾部
  // 残留半行不再 emit:平衡截断(括号恰好闭合)能骗过 parse、误把崩溃当正常完成;交 #handleExit 拒在飞请求
}
  • 代码什么意思
  • 分包(跨读半行):buffer 跨 read 累加,没出现 \n 就不 emit,继续等下一段。
  • 粘包(一读多行):while (indexOf("\n")!==-1) 把一块里的多行逐行切出来。
  • 多字节字符不截断:TextDecoder {stream:true} + 末尾 decode() flush,避免半个汉字被拆。
  • CRLF 兼容:.replace(/\r$/,"") 去掉回车,不污染 JSON。
  • 退出半帧(已修正):④ 若在写出一条消息途中崩溃,管道 EOF 时残留的半行不再当消息 emit——因为平衡截断(括号恰好闭合的半行)能骗过 JSON.parse、被误当成正常响应 resolve 一个在飞请求,把崩溃伪装成正常完成。直接丢弃,由 #handleExit 把在飞请求判失败。
  • 对抗审计揪出的三处缺陷(均已修):① 平衡截断误 resolve(见上一条);② handler 抛错会杀掉整条 stdout 读循环、静默丢光后续帧——已用 try/catch 包住 onLine;③ 并发写因 stdin writer 锁竞争丢帧(见下 #write)——已用 #writeTail 串行化。另:行长上限防超长无换行失控(超即拒+杀),与 Ora 侧 8MB 对齐。
为什么需要 #write 串行化#write 每次独占 stdin 的 writer;两个并发写(一个在飞 request 写 + 一个 session/cancel 通知写,或两个权限回包)会让第二个 getWriter() 抛 "locked"、那帧丢失。用一条 Promise 链把所有写排成队列,同一时刻只有一个 writer。
wire.ts · #write 写端串行化
#writeTail: Promise<void> = Promise.resolve();

async #write(line: string) {
  const proc = this.#proc;
  if (proc === undefined) throw new Error("ACP wire is not started");
  const encoded = new TextEncoder().encode(line);
  const write = this.#writeTail.then(() => {
    const writer = proc.stdin.getWriter();        // 排到队首才取锁,不会撞
    return writer.write(encoded).finally(() => writer.releaseLock());
  });
  this.#writeTail = write.catch(() => undefined); // 一次写失败不坏整条链
  return write;
}
  • 代码什么意思
  • #writeTail 链:每个写挂在上一个写完成之后,串行执行;getWriter 只在队首调用,绝不和未释放的锁撞。
  • 失败不连坐:某次写失败用 .catch 兜住,#writeTail 保持 resolved,后续写照常排队;真正错误经返回的 write 传给调用方。
结论(经对抗验证修正)Ora 侧(长度前缀+8MB+分配前校验+半帧报错)sound;ACP 侧粘包/分包主轴 sound,但对抗审计揪出 3 处韧性/正确性缺陷(平衡截断误 resolve、handler 抛错杀读循环、并发写丢帧),均已修。

2.2 桥的六个零件(每个:为什么需要 → 代码 → 什么意思)

桥代码拆成六个文件,各管一摊。下面对每个零件讲:它解决什么问题、关键代码、逐点解释。

2.2.1 wire.ts — 和 ④ 的收发管道

为什么需要桥要跟 ④(Claude Code 进程)用 ACP 通信:给 ④ 发指令、收 ④ 吐的字。需要一个专门管"拉起 ④ 进程、按行收发 JSON-RPC、④ 崩了把在飞请求判失败"的模块。它绝不碰 Ora 自己的 stdout(那是 ②↔③ 专用的)。
wire.ts · 请求与退出处理
request(method, params) {
  if (this.#exited) return Promise.reject(new AgentProcessExitedError(null,null));
  const id = this.#nextId++;                      // 单调递增的请求 id
  return new Promise((resolve, reject) => {
    this.#pending.set(id, { resolve, reject });    // 登记等回包
    this.#write(frameRequest(id, method, params)).catch(reject);
  });
}

#handleExit(code, signal) {
  if (this.#exited) return;
  this.#exited = true;
  for (const p of this.#pending.values())          // ④ 崩了:所有等回包的请求全判失败
    p.reject(new AgentProcessExitedError(code, signal));
  this.#pending.clear();
  this.#handlers.onExit(code, signal);
}
  • 代码什么意思
  • request:每发一条 ACP 请求就分配一个 id,登记到 #pending 等回包;返回 Promise,④ 回包时 resolve。
  • #handleExit:④ 一旦退出(崩了/正常退出),把所有还在等回包的请求统一 reject 成"agent 进程退出"错误,上层就能报成 agentProcessFailed。
  • 不碰 process.stdout:④ 有自己的私有管道,它的输出不会漏到 ②↔③ 那根线上。

2.2.2 queue.ts — 有界缓冲队列

为什么需要④ 吐字很快(一秒上万字),② 收得慢(还要写帧、走 HTTP、前端渲染)。中间没有缓冲,④ 会被自己的输出管道堵死(死锁)。需要一个有界队列当蓄水池,满了就丢最不重要的(半截字),保住重要的(工具调用/用量)。
queue.ts · push 的丢老保新策略
push(item) {                       // 返回 true=持续溢出,该喊停
  if (this.#buffer.length < this.#capacity) { this.#buffer.push(item); return false; }
  const i = this.#buffer.findIndex(e => this.#isDroppable(e));   // 找最旧可丢的
  if (i !== -1) { this.#onDrop(this.#buffer.splice(i,1)[0], "evicted"); this.#buffer.push(item); return this.#bump(); }
  this.#onDrop(item, "overflow"); return this.#bump();           // 全是边界事件 → 丢新来的
}
pushTerminal(marker) { /* 终态标记无条件下发,绕过丢策略 */ }
  • 代码什么意思
  • 丢老保新:满了优先丢最旧的"可丢项"(中间的半截字 TextDelta),腾位子放新的。
  • 不丢边界事件:工具调用、用量、终态这些不能丢;若缓冲里全是边界事件,宁丢新来的也不破坏已有。
  • 持续溢出喊停:丢到一定次数返回 true,上层就主动取消这轮,不让 ④ 堵死。
  • pushTerminal:一轮结束的终态标记走专用通道,绝不被丢。

2.2.3 translate.ts — ACP↔Ora 事件翻译(纯函数)

为什么需要④ 吐的是 ACP 的 session/update(一堆英文变体),Ora 认的是 AgentEvent(6 种)。要一张映射表把前者翻成后者;翻不了的(无关变体)显式丢弃并计数,不静默。
translate.ts · 关键映射表
stopReasonToFinishReason:                       // ④ 的收尾原因 → Ora 的
  end_turn → completed
  refusal   → completed  (+ 先发一个 Status{phase:"refusal"} 提示)
  cancelled → cancelled
  max_tokens / max_turn_requests → limit

sessionUpdateToAgentEvents:                     // ④ 的事件 → Ora 的事件
  agent_message_chunk → TextDelta{channel:"assistant"}    // AI 说的字
  agent_thought_chunk  → TextDelta{channel:"reasoning"}   // AI 想的过程
  tool_call            → ToolCall{callId, name, summary}   // 调了工具
  tool_call_update     → ToolResult{callId, isError, summary} // 工具结果
  usage_update         → Usage{...}                       // token 用量
  user_message_chunk / plan / *_update → drop + 计数      // 翻不了的丢弃
  • 代码什么意思
  • 收尾映射:④ 说"正常说完"→Ora 的 completed;"到上限"→limit;"被取消"→cancelled。refusal(拒绝)特殊:Ora 没专门字段,先补发一条 Status 提示再 completed。
  • 事件映射:AI 的字→文本增量;调工具→工具调用;结果→工具结果;用量→用量事件。前端的字、工具卡片、用量都从这来。
  • 显式丢弃:Ora 不关心的变体(user_message_chunk/plan 等)不静默吞,计数告警,方便排查。

2.2.4 client.ts — ACP 会话客户端(核心)

为什么需要这是桥的大脑:开 ACP 会话、跑一轮、把 ④ 回吐路由到对的在飞轮次、处理权限请求、处理 ④ 崩溃。它把"一次对话调用"编成一个流式生成器,边收 ④ 的事件边往外 yield。
client.ts · initialize 广告 + 权限放行 + 一轮生成器
// 拉 ④ 时广告:文件/终端我都替不了,你自己干(ADR-0001)
await this.#wire.request("initialize", {
  protocolVersion: 1,
  clientCapabilities: { fs:{readTextFile:false,writeTextFile:false}, terminal:false },
});

// ④ 调工具前来问"行不行" → v1 自动放行
if (method === "session/request_permission") {
  const chosen = options.find(o => o.kind==="allow_once") ?? options[0];
  return wire.respond(id, { outcome:{outcome:"selected", optionId: chosen?.optionId ?? "allow_once"} });
}

// 一轮:发 session/prompt,响应落地时把终态标记经 pushTerminal 下发
async *runTurn(sessionId, blocks, signal) {
  const queue = new BoundedEventQueue(...);
  const done = this.#wire.request("session/prompt", { sessionId, prompt: blocks });
  done.then(r => queue.pushTerminal({ __oraTurnEnd:true, stopReason:r.stopReason }),
            e => { turnError = e; queue.close(); });
  for (;;) {
    const item = await queue.pull();
    if (item === undefined) throw turnError ?? new AgentProcessExitedError(null,null);
    if ("__oraTurnEnd" in item) { stopReason = item.stopReason; break; }
    yield item;                                  // 流给 provider → runtime → ②
  }
  return { stopReason };
}
  • 代码什么意思
  • initialize 广告:明确告诉 ④"我不替你读写文件/跑终端",所以 ④ 自己干 I/O;这样我们也就不会收到 fs/terminal 请求。
  • 权限放行:④ 想调工具前会问,我们 v1 自动选 allow_once 放行,④ 自己执行(详见 2.3)。
  • runTurn 生成器:发 session/prompt 后,把响应落地时刻当成"这轮结束"信号,经队列下发终态标记;循环从队列拉事件 yield 出去,直到拉到终态标记。
  • ④ 崩溃:队列被关、pull 返回 undefined → 抛 AgentProcessExitedError,上层报 agentProcessFailed。

2.2.5 provider.ts — Ora 眼里的 AgentProvider

为什么需要Ora 不认识 ACP,只认"AgentProvider"这个接口(8 个方法)。桥要用这个接口把 ④ 包装起来,让 Ora 调"开始对话"时,桥去开 ACP 会话+跑 prompt,并把事件流回给 Ora。一个 provider 持一个 ④,跨会话复用。
provider.ts · startConversation(手动步进生成器)
async *startConversation(call, request) {
  const { cwd } = scopeToCwd(request.scope);
  const sessionId = await client.newSession(cwd);     // 开 ACP 会话
  const conversationId = sessionId;                    // 直接当 Ora 的会话 id
  yield { kind:"conversationStarted", conversationId };

  const gen = client.runTurn(sessionId, promptToAcpBlocks(request.prompt), call.signal);
  let response;
  for (;;) {                                  // 手动步进,而非 for await...of
    const step = await gen.next();
    if (step.done) { response = step.value; break; }
    yield step.value;                         // 每个事件转给 Ora
  }
  if (response.stopReason === "refusal") yield refusalStatusEvent();
  return { conversationId, finishReason: stopReasonToFinishReason(response.stopReason) };
}
  • 代码什么意思
  • 开新对话:scope 里取工作目录 → 开 ACP 会话 → 会话 id 当 Ora 的 conversationId(一一对应)。
  • 手动步进:用 gen.next() 一步步拉,边拉边 yield 给 Ora。为什么不用 for await...of?因为它会丢掉生成器的返回值(终态 PromptResponse),手动步进才能拿到。
  • refusal 处理:若 ④ 拒绝,先补发一条 Status 提示,再返回 completed。
  • 终态:把 ④ 的 stopReason 翻成 Ora 的 finishReason 返回,这轮结束。

2.3 权限:agent 要动你文件时怎么办

Claude Code 干活时要读你的文件、改代码、跑命令。ACP 有两套相关机制,别混:

机制是什么本方案怎么选
fs / terminal(委托)true=桥替 ④ 读写文件/跑终端关(false):④ 自己干 I/O
request_permission(门禁)④ 调工具前问"行不行"v1 自动放行(allow_once)+日志

2.4 背压:agent 吐太快怎么办

见 2.2.2 queue。人话再讲一遍:④ 一秒吐上万字,② 来不及收,④ 会堵在自己输出管道上死锁。桥中间放个有界队列当蓄水池,满了丢最旧的半截字(不丢工具/用量/终态),持续堵就主动取消这轮。
